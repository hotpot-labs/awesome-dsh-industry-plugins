# DeepSeek Harness (DSH) 插件筛选标准
本标准针对 DSH 插件生态开源开放、社区贡献为主、安全边界模糊的现状，从**基础准入、技术质量、安全合规、可维护性、功能价值**五个维度建立分级筛选规则，适用于个人开发者、企业团队对 DSH 插件进行选型与准入管控。

## 一、基础准入标准（一票否决项）
本维度为插件准入的最低门槛，任意一项不满足直接排除。

### 1. 来源与作者可信
- **发布渠道**：必须托管于 GitHub 等公开可追溯的代码平台，支持完整提交历史回溯；禁止来源不明的离线安装包、第三方网盘分发的闭源插件。
- **作者资质**：优先选择有持续开源贡献记录的开发者/组织；规避匿名账号、注册时间小于 7 天、无其他项目历史的一次性账号发布的插件。
- **社区背书**：优先纳入官方社区推荐、知名开发者验证、高 Star（≥100）且无重大负面 Issue 的插件。

### 2. 开源协议与合规性
- 插件需采用与 DSH 主框架（MIT 协议）兼容的开源许可（MIT、Apache 2.0 等），禁止 GPL 强传染协议插件进入商用环境。
- 代码无明显侵权内容，未抄袭其他开源项目且未标注来源。
- 插件功能不违反当地法律法规，不包含破解、爬取敏感数据、绕过权限限制等违规能力。

### 3. 功能真实性
- 插件描述与实际能力一致，不存在“标题党”“虚假宣传”，无捆绑安装无关功能。
- 核心功能可通过源码直接验证，不依赖未公开的第三方服务实现核心逻辑。

## 二、技术质量标准
### 1. 架构与规范兼容性
- **DSH 版本兼容**：明确标注支持的 DSH 核心版本范围，兼容当前主流稳定版（如 0.1.x 系列），不依赖已废弃的内部 API。
- **Cordis 规范遵循**：严格遵循 Cordis 元框架的插件开发范式，通过官方服务与事件机制交互，不直接修改内核源码、不通过 Hack 方式绕过插件生命周期管理。
- **插件间兼容性**：与 DSH 官方内置插件、主流社区插件无已知功能冲突；若存在冲突需在文档中明确标注规避方案。

### 2. 性能与资源占用
- **启动开销**：插件初始化耗时不超过 500ms，不显著拖慢 DSH 整体启动速度。
- **运行时资源**：空闲状态下额外内存占用 ≤ 50MB，无后台常驻轮询、死循环等异常 CPU 占用。
- **资源释放**：插件卸载/禁用后可完整释放内存、定时器、事件监听，无内存泄漏与残留进程。

### 3. 代码质量与稳定性
- 代码结构清晰，核心逻辑无严重冗余、无大量注释掉的废弃代码。
- 具备完善的异常捕获机制，单个插件报错不会导致 DSH 主进程崩溃、会话中断。
- 关键操作具备幂等性，重复执行不会产生脏数据或异常状态。

## 三、安全合规标准（核心管控维度）
### 1. 权限最小化原则
插件申请的系统能力必须与自身功能强相关，禁止超范围申请权限：
- **文件系统权限**：仅允许访问工作区指定目录，禁止读取系统敏感文件（如 `~/.ssh`、环境变量配置、浏览器凭证）；全局文件读写权限需严格论证必要性。
- **命令执行权限**：禁止无限制的 `child_process` 调用；若需执行系统命令，必须限定命令白名单，禁止拼接用户可控输入直接执行。
- **网络权限**：明确所有对外请求的域名与用途，禁止无理由的外发数据、反向连接；禁止内置代理、挖矿、远控类网络能力。
- **模型与会话权限**：禁止无授权读取全局会话历史、窃取 API Key、篡改模型配置；仅允许访问当前会话上下文。

### 2. 代码与依赖安全
- **源码可审计**：核心逻辑全部开源可读，禁止使用混淆代码、加密脚本、远程动态加载执行的代码。
- **依赖安全**：
  - 第三方 npm 依赖数量可控，避免超过 3 层的深层嵌套依赖；
  - 无已知高危漏洞（可通过 `npm audit` 校验），不使用已废弃、停止维护的依赖包；
  - 禁止引入 `eval`、`vm` 等可执行任意代码的危险依赖与写法。
- **后门排查**：无隐藏的定时任务、数据上报、文件窃取逻辑；无调试端口、后门指令等未公开能力。

### 3. 数据安全与隐私
- **本地优先**：默认所有数据处理在本地完成，核心业务数据不上传第三方服务器。
- **数据采集透明**：若存在数据上报（如错误统计、使用分析），必须在文档中明确告知采集内容、接收方、用途，并提供关闭开关。
- **敏感数据保护**：禁止读取、上传用户的 API Key、代码仓库内容、本地文档等敏感信息；涉及工作区文件操作必须留痕可查。

### 4. 运行时隔离
- 优先支持 DSH 官方沙箱机制运行，不强制要求管理员/root 权限。
- 不修改系统全局配置、不注入其他进程、不创建开机自启项。

## 四、可维护性标准
### 1. 维护活跃度
- **更新频率**：近 3 个月内有版本更新或代码提交，长期（≥6 个月）未维护的插件纳入灰名单。
- **Issue 响应**：开发者对 Bug 反馈、安全问题的响应周期 ≤ 7 天，高危安全问题有修复记录。
- **弃用风险**：无明确“停止维护”“不再更新”标注；若作者声明弃用，直接排除。

### 2. 文档与易用性
- 提供完整的 README，包含：功能说明、安装/卸载方式、配置项说明、使用示例、注意事项。
- 配置项具备默认值，无需复杂手动修改即可使用核心功能。
- 有明确的版本变更日志（CHANGELOG），可追溯每个版本的功能与安全更新。

### 3. 社区与反馈
- 无大量重复的 Bug 反馈、安全投诉、恶意行为举报。
- 下载量/使用量与插件复杂度匹配，避免“零使用”的冷门插件直接进入生产环境。

## 五、功能价值标准
### 1. 必要性与不可替代性
- 解决明确的业务痛点，避免“为了装而装”的冗余插件；同类功能插件只保留最优 1 个。
- 优先选择官方能力缺失、且无法通过简单配置替代的插件（如特定工具链集成、UI 核心增强）。

### 2. 场景匹配度
- 个人使用：可适度放宽维护性要求，优先满足功能需求。
- 企业/团队使用：必须满足全部安全要求，且经过内部测试验证，禁止直接安装社区未审计插件。

## 六、分级准入与筛选流程
### 1. 插件分级
| 分级 | 适用范围 | 准入要求 |
|------|----------|----------|
| 白名单 | 企业生产环境、核心工作区 | 满足全部标准，经过完整安全审计，作者可信 |
| 灰名单 | 个人测试、非敏感场景 | 满足基础准入与核心安全要求，维护性一般，无高危风险 |
| 黑名单 | 禁止安装 | 存在恶意行为、超权限、安全漏洞、虚假宣传等问题 |

### 2. 标准筛选流程
1. **初筛**：校验来源、开源协议、功能真实性，剔除明显不合格项。
2. **技术复核**：验证 DSH 版本兼容性、性能开销、插件冲突情况。
3. **安全审计**：人工审查权限申请、核心代码、依赖链，排查恶意逻辑与数据外发行为。
4. **功能验证**：在隔离测试环境中安装运行，验证实际能力与描述一致。
5. **分级入库**：根据结果划入对应名单，定期复审计入维护状态。

### 3. 定期复审
- 白名单插件每 3 个月复审一次，灰名单插件每 1 个月复审一次。
- 出现安全漏洞、作者弃用、负面反馈集中的插件，立即降级或加入黑名单。
